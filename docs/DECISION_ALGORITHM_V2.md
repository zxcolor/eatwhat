# 决策算法 V2：有证据的条件判定与少量可解释备选

设计日期：2026-09-08。适用范围：现有 Android 路线图中的单人决策、同设备匿名群组、区域模型门槛和商户认领数据。本文区分现有行为、当前修复与后续待实现设计；不将设计文档或合成测试等同真实用户效果、供应商授权或公开发布验收。

## 1. 产品目标和成功含义

用户应能用一次请求了解：哪些已知条件得到满足，哪些条件仍需确认，为什么出现这一个主选，以及另两个选项有什么具体差别。明确冲突不能被评分、模型或商户身份覆盖；数据不足不能被包装成确定结论。

“不出错”落实为可验证的不变量、反例回归和事实边界。系统不承诺实际消费、到店营业、座位、排队或按时返回；没有相应证据时必须直接显示待确认。`fitScore` 是同策略内的规则分值，`confidence` 是当前字段完整程度，二者都不是满意概率。

## 3. 每种输入必须有明确作用

效果分为查询、过滤、排序、解释、暂不支持。界面仅展示当前可信能力能兑现的输入；隐藏控件时同时清除旧草稿中的不适用值。

| 输入 | 当前作用与边界 |
|---|---|
| 起点、半径 | 影响实际查询并复核距离；坐标系一致。半径不是路线可达性保证 |
| 餐段、专项 profile、主动体感 | 只通过已声明的 provider 原子能力查询；不支持就拒绝，不静默换成午餐。主动体感不是自动天气 |
| 预算 | 已知来源参考人均超过上限时过滤；参考人均低于上限只证明参考值，不证明实际总支出 |
| 可用时间、交通 | 以距离和固定速度估算往返，再加规则用餐估时；缺路线、等位等事实，当前不作为绝对硬过滤 |
| 这次不吃 | 排除类别；父子分类规则保持 API/Kotlin 一致。不是配料、过敏或饮食认证 |
| 更想吃、偏好向量、探索 | 只有实际具备排序或相应查询能力时生效；本分支保证规则路径的集合选择等权。Qwen 路径仍需补输入规范化与显式偏好约束，不能据此声称全路径置换不变 |
| 人数 | 参与场景意图和群组共同约束；不能推断座位、包间或预约能力 |
| 同条件重试 | 完全相同条件的新请求；可能相同，不当负反馈或跨请求反重复学习 |
| 私有反馈 | 现有持久化能力不等于已接入学习；读取、关联、派生用途与删除传播分别验收 |

## 4. 统一决策流程

```text
本轮明确输入
  -> 能力与版本检查
  -> 用途授权与有界查询计划
  -> 来源适配和字段证据规范化
  -> 明确冲突过滤与逐项证据判定
  -> LIVE 来源顺序 / 获授权的确定性排序
  -> 少量主备选与结构化解释
  -> 返回前授权、能力和请求代次复核
  -> Android 独立复核后展示
```

AI 只能辅助解释用户已表达的方向，不能制造或修改价格、距离、营业、评分、座位等事实。规则与 AI 路径共用同一约束判定器。Qwen 当前仍可返回不同菜系权重；后续要在模型输入前规范化无序选择，并在返回后约束其不能把用户的等权集合解释为用户声明的先后顺序。这项全路径语义尚未由本分支证明。取消、配置改代、撤权或隐私撤回后，晚到响应不得回写。

## 5. 逐项证据三态

拟新增版本化 `ConstraintAssessment`，至少包括 `dimension`、`state`、`scope`、`evidenceKind`、`explanationCode`、`ruleVersion`，有可靠来源时才包含 `observedAt` 和 `validUntil`。公开结构不包含稳定外部地点 ID、材料路径、成员身份或精确位置副本。

- `MATCH`：只在明确作用域内有足够证据。例如“来源参考价不高于预算”，不能缩写为“保证在预算内”。
- `CONFLICT`：明确事实与已定义条件冲突，或估计超出时限；必须区分硬冲突与估算风险。
- `UNKNOWN`：必要信息缺失、过期、含矛盾或未完整理解。它不等于零、不等于便宜，也不等于条件通过。

营业文本包含未理解的日期、临时休业或混合片段时，不能仅凭一个可识别时间段推断完整营业状态。结束分钟语义没有依据时保守待确认。全日、跨夜、相邻时段、无效小时与分钟需各有独立回归。

现有时间和参考人均语义先保持兼容；未来若新增“必须实际在某预算/时限内”的严格选项，要新增明确契约及证据要求。无法证明时返回无法确认，不能偷偷降低条件。旧客户端收到其能理解的版本，缺能力字段时失败关闭。

## 6. 查询完整性与数据权利

查询有最大调用数、候选数和总 deadline。分页只在官方能力、授权和配额允许时使用；不能借补页做批量爬取。只查部分候选时，无结果文案应为“本次查询未找到符合已知条件的选项”，不声称整个区域不存在餐厅。

同一来源的请求内去重使用内部 `(provider, providerPlaceId)`。跨来源物理门店匹配需要独立证据，不能只按名称相似合并。请求 token 不能转为跨请求稳定哈希以绕过持久化限制。

`LIVE_DISPLAY_ONLY` 继续保留来源顺序、`fitScore=null`，未知字段不能成为暗中重排理由。展示、重排、持久化引用、模型处理、训练、评估和推理分别检查实际用途；商户自有字段与第三方字段分别追溯，不能因拼接而共享授权。异步调用前及采用结果前再次检查权利。

## 7. 获授权的单人主备选策略

这一节为后续策略提案，当前分支不冒充已实现。

1. 先执行硬约束和证据判定；明确硬冲突永远不能补回备选。
2. 只在同一作用域和证据要求下比较候选。已知与未知差异直接展示，不能用一个总分遮住关键缺证。
3. 软排序使用版本化规则和用户明确权重。缺字段采用固定策略和共同分母，不删除维度再归一化，使缺数据者无故获益。
4. 主选说明具体依据，备选至少有一个可核对差异：参考价、距离、时间估计或明确类别。没有有效差异允许少于三个，不凑数。
5. 平分按稳定来源顺序处理，保持可重现。商户是否认领、是否付费不能增加质量分；公开点评、支付和推广仍另立项目。

## 8. 同设备匿名群组策略

保留 2–8 人、共同起点和交通、固定午餐、匿名内存态的范围，不增加房间、邀请或投票。

第一层维持可独立重算的共同约束：预算/时间/半径取适用最小值，排除取并集。任何人的明确排除都不能被多数覆盖。成员顺序变化不能改变结果；新增更严格成员不能扩大可行候选集。无共同软偏好不等于没有可吃餐厅。

第二层拟采用 `GROUP_EXPLICIT_PREFERENCE_COVERAGE_V1`，仅在合法可排序且有有效分类证据时运行：

- 没表达偏好的人保持中立；未知分类不算匹配，也不伪装成已知不匹配。
- 先在可比较候选中确定主选；备选组合以覆盖不同成员的明确选择为目标，展示“这三个选项覆盖了哪些已表达口味”。它不是心理满意度，也不是抵抗虚假成员的公平机制。
- 对有界候选集枚举最多三个选项的组合，以明确覆盖的成员数为首要组合指标；其次比较有效类别差异及已定义的规则排序，最后按稳定来源顺序打破平局。候选上限和超限策略必须在实现时固定并测试，不能默默丢掉更严格成员。
- 主选只描述该候选实际覆盖的成员，不用备选组合的覆盖数给主选贴“所有人满意”标签。只有一个人有偏好、完全相反偏好、无交集、同名标签未知、全部无偏好都分别验收。
- LIVE 仍只按来源顺序展示共同约束后的候选，不运行该覆盖重排。成员输入不进入账号、事件、模型或持久化。

## 9. 反馈与冷启动

没有历史时用本轮条件和可解释规则。主动保存的个人偏好可清除；不能按人口信息或位置猜饮食禁忌。

事件语义固定：展示不等于喜欢，导航不等于到店，用户自报已吃不等于独立核验，无原因重试不等于负反馈。价格过高、距离不合适和事实纠错分别处理。稳定地点关联和模型用途未获授权时不接入跨请求学习；不能因为数据已写入私有记录就默认允许训练。

后续学习必须先记录合法曝光策略与样本选择方式，再做固定评价集和受控实验。仅观察已展示餐厅的点击无法直接证明新策略优于旧策略。删除、注销或撤权要传播到派生特征、数据集资格和模型采用状态。

## 10. 区域模型与商户事实

区域门槛是治理功能，不代表已经训练了区域模型。需要独立的地区识别、任务/模型/数据/策略版本、用途授权、样本设计、评价结果、有效期和管理员审查。评估通过、获准采用、实例可执行、本次实际执行是四个不同状态。当前没有已注册可执行区域模型时必须返回未执行并使用基础规则。

指标方向、最低样本和性能门槛先登记再评估。初始产品门槛、实验所得门槛和合成测试参数分别标明；证据不足拒绝采用，不填写虚构效果值。到期、撤权、实例校验失败、地区不明或不匹配都回退。覆盖配置中的全国标记不能推断请求地区。

商户认领分别核验经营主体、申请人代表权和具体门店。登录或材料上传不直接生成管理权；申请、审核、管理权、事实修订和发布分别有状态及审计。一次获批归属不证明该店食品安全、价格或营业事实永远正确。

商户提供的资料使用独立第一方门店 ID，注明来源与有效期。与第三方资料冲突时标记待核验，不静默覆盖。失去管理权后禁止编辑/发布；过期事实降低为待确认。证据材料仅供受限审核，不进入推荐特征或公开日志。数据库唯一归属、并发批准、跨账号越权、注销清理和新 schema 的可用回退版本必须真实验收。
