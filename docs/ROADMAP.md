# 实施路线

## 12 周 Android 首测版

### 第 1–2 周：产品、设计、契约和资质

- 固化 PRD、页面流、数据字典、验收标准和暖橙/奶油白设计令牌。
- 访谈至少 10 名学生、5 名教师，验证午餐预算、时间和路程模型。
- 确定包名；申请高德、百炼、短信、微信开放平台、QQ 互联和 EMAS。
- 提交高德书面授权工单；建立权限矩阵、数据权利矩阵和 SDK 清单。
- 交付可点击原型、OpenAPI 初稿和数据授权风险报告。

### 第 3–4 周：基础工程和账号

- 完成 Android Compose 架构、设计系统、手动选址、前台定位、游客身份。
- 建立阿里云北京测试环境、PostgreSQL/PostGIS、OSS 和 SLS。
- 实现手机号 + 微信双验证注册、QQ/邮箱绑定框架、令牌轮换、限流、脱敏和注销。
- 验收：真机可游客进入、定位、注册、退出和注销。

### 第 5–6 周：推荐闭环

- 完成三餐、预算/时间、交通和覆盖规则。
- 接入高德实时搜索与千问结构化意图，失败确定性回退。
- 落地数据权利双模式、结果卡和“为什么推荐”。
- 建立 200 场景黄金集的初版。
- 验收：北京、上海等不同城市的真实推荐均可完成决策，无结果和上游不可用有明确说明。

### 第 7–8 周：完整 1.0 能力

- 推荐起点的地点关键词选择、Top 3 列表/附近方位图、本地筛选、详情、收藏和账号历史。Android 1.0 不开放直接餐厅关键词搜索或完整地图浏览；游客本机数据不静默上传或合并，未来若立项合并必须先补明确同意、冲突、幂等、撤销与删除语义。
- 分享推荐卡不属于 Android 1.0；契约字段与底层实现仅封存，最早在 2.0 经新的产品、数据权利、隐私和安全评审后再决定是否重启。
- 可选账号工程候选包含手机号注册/登录、已绑定邮箱/微信/QQ 登录，以及登录后邮箱/微信/QQ 绑定；生产入口仍按服务端原子能力失败关闭。另含设置、反馈、AI 开关和隐私控制。
- Android 1.0 不开放账号恢复；后续版本不得复用隐藏入口，必须重新立项与安全评审。
- 运营台 RBAC/MFA、规则/提示词版本、功能开关、审计和成本诊断。
- 验收：Android 1.0 功能清单逐项通过。

### 第 9–12 周：质量、Alpha、Beta 和发布准备

- 核验 300 家样本餐厅；做弱网、无障碍、性能、内存、安全和恢复专项。
- 第 10 周约 20 人 Alpha，第 11 周扩至 50–100 人 Beta。
- 第 12 周只修复问题，完成部署、回滚、告警、客服、应急、官网政策页、SBOM 和 APK 哈希。
- 未完成 App 备案和数据授权时不得公开发布 APK。

## Android 后续版本

- 1.1：私有结构化反馈、可控偏好向量、桌面小组件、主动场景模式，以及诚实的同条件重新请求。跨请求反重复仍待合法稳定地点关联能力后实现；当前不把可能相同的重新请求冒充“换一批”。
- 1.2：早餐/晚餐专项、奶茶/咖啡/甜品独立版本化 profile（不是独立训练模型）及请求级用户主动体感。当前只完成代码/JVM 候选：垂类和主动体感按 provider 原子能力声明失败关闭，AMAP 暂只支持三餐 + `NONE`，完整候选可在 development/test DEMO 验证但 production 禁止 DEMO。用户体感不读取实时天气、温度或后台位置，不持久化；特殊 profile 强制规则、AI 关闭。真实自动天气、设备、生产与供应商分类授权闭环仍未完成，因此 1.2 不能标记为完成。
- 2.x：匿名群组决策、区域模型门槛、商户认领；公开点评/支付/推广另立项目评审。

## 跨平台顺序

按用户在计划正文中的最新明确要求：

1. Android 核心稳定运行至少 30 天并冻结 API v1。
2. 开发原生 TypeScript 微信小程序，共用推荐、账号、收藏和历史；完成微信隐私接口适配。
3. 小程序稳定后开发 Swift/SwiftUI iOS；提供 Android 同等核心能力及符合审核规则的 Apple 登录。

每个平台维护功能对照表。系统登录、导航和权限 UI 可以平台化，推荐事实、排序规则和主结果必须保持一致。任何平台的分享能力都不是 1.0 默认范围，必须在 2.0 评审后单独立项。
